# 20 — 根据验证结果继续修复

**What to build:** Agent 能在修改后运行获批验证，理解失败输出，再次调查和修改，直至验证通过或达到明确限制，从而形成首个完整仓库级软件工程闭环。

**Blocked by:** 19 — 经逐次审批运行命令

**Status:** resolved

- [x] 模型在后续轮次收到结构化命令结果并能据此修改方案。
- [x] 一次任务可完成调查、修改、验证失败、再次修改和验证成功。
- [x] 每次新命令仍独立审批，Agent 迭代不能扩大已批准范围。
- [x] 达到循环、工具、命令输出或上下文限制时准确停止。
- [x] CLI 最终报告变更证据、验证结果、运行统计和未完成原因。
- [x] 端到端测试以真实临时仓库证明修复闭环，无人工代改代码。

## Implementation result

- Agent 运行时维护 `clean / required / failed` 验证状态；文件变化或修改型命令后必须有更新且成功的明确验证，验证失败或末次修改后未验证时分别以 `verification_failed` / `verification_required` 拒绝 `RunCompleted`，不再依赖模型仅遵守提示词。
- `run_command` 增加结构化 `purpose`（`inspect / verify / build / modify / other`），并绑定到审批指纹；只有 `purpose=verify` 进入验证历史并能清除待验证状态，普通调查命令不再显示成“验证通过”。
- `ToolResult` 与 `ToolCompleted` 增加实际变更路径、退出码、超时、输出截断、命令用途和追踪完整性摘要；原子替换、批量写入和移动均在副作用成功的瞬间记录路径，后置读取或哈希失败也不会漏报已经发生的效果。
- 获批命令执行前后对普通授权工作区做有界文件快照，报告新增、修改和删除路径；敏感/跳过目标或容量边界无法可靠覆盖时标记追踪不完整，CLI 使用保守名称“Wesly 记录的工作区变更”，不宣称覆盖工作区外副作用。
- CLI 在完成时汇总实际变更路径、全部命令验证结果和模型/工具/token 统计；未完成时保留停止原因，并增加最后动作、已有变更、已有验证、模型/工具统计和针对停止类型的建议。
- 命令仍沿用 Ticket 19 的一次性批准对象；同一验证命令执行两次也产生两个独立审批请求，不共享批准或扩大参数、工作目录与环境范围。
- 现有 `turn_limit`、`tool_limit`、`context_limit` 和命令输出截断合同保持不变；输出截断状态会进入 CLI 验证摘要，达到硬限制时不伪装为任务完成。
- 端到端测试创建真实临时 Git 仓库，由脚本化模型依次读取文件、做出错误修改、运行真实失败验证、接收 `command_nonzero`、重新读取和修正、再次运行真实成功验证并给出文件引用；测试过程中没有人工代改仓库文件。
- 另一个端到端路径在首次验证失败后注入模型服务故障，证明 CLI 仍准确报告未完成原因、最后失败验证、已产生的变更和运行统计。
- 审查回归覆盖：模型在修改后不验证、验证失败后直接结束、验证成功后再次修改、普通命令不冒充验证、命令创建文件、原子替换后置读取失败、批量写入后置哈希失败、移动后置哈希失败，以及敏感文件快照不完整标记。
- 完整测试为 `120 passed, 4 skipped`，`mypy src` 严格检查通过。
