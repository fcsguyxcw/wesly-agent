# Wesly 开发流程

## 协作分工

- 用户负责架构取舍和代码审查。
- Codex 负责实现、测试、文档、验证、提交和推送。
- 规格、有效 ADR 和当前实施票据共同限定每次工作的范围。

## 一张票的完成流程

1. 从本地 tracker 选择阻塞项均已解决的最小编号票据。
2. 将票据状态改为执行中，只实现该票据描述的端到端行为。
3. 在已经接受的公共测试缝上执行红—绿 TDD，不伪造 Agent 内部模块。
4. 运行严格类型检查、相关测试和完整测试套件。
5. 需要真实供应商能力时，执行显式且有界的 DeepSeek smoke。
6. 分别按代码标准和票据规格进行双轴审查，并修复阻塞发现。
7. 将票据验收项勾选完成，状态改为 `resolved`，记录验证结果。
8. 提交该票据产生的代码、测试和文档，并推送到 GitHub。

## 提交与范围规则

- 每张实施票至少产生一个可追溯提交；审查修复可以追加小提交。
- 完成票据后必须推送，确保 GitHub 默认分支包含最新已验收代码。
- 不在当前票据中提前实现后续架构；只允许建立已被 ADR 要求的稳定接缝。
- 不提交 API key、`.env`、虚拟环境、缓存、本地数据库、构建产物或未进入正式决策链的探索草稿。
- 不使用笼统的 `git add -A` 处理混合工作区；只暂存已确认属于本票的文件。
- 远程写入、部署或创建外部资源必须有用户明确授权。
